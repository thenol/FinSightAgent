# 功能架构与模块拆分

## 1. 拆分原则

系统以业务能力拆分，而不是以 Agent 数量拆分。Agent 是“研究工作流”中的可替换执行单元，数据采集、事件管理、证据存储、发布、权限和评估均属于独立的确定性功能模块。

模块拆分遵循以下原则：

- 单一职责：一个模块只拥有一类核心业务对象。
- 明确边界：跨模块通过 API 或领域事件交互，不直接修改对方数据。
- 确定性优先：能够用规则、查询或计算完成的能力不交给模型。
- 可独立演进：Agent、模型和提示词升级不影响事件、证据和报告的稳定标识。
- 全程可追溯：任何结论都能回溯到事件、证据、Agent 运行和模型版本。

## 2. 一级功能域

| 功能域 | 核心职责 | 核心对象 | MVP |
| --- | --- | --- | --- |
| 数据接入 | 获取、清洗、标准化外部信息 | Source、Document | P0 |
| 事件中心 | 去重、聚类、分类、实体对齐和事件生命周期管理 | Event、Entity、EventDocument | P0 |
| 证据与知识中心 | 保存来源、原文、事实、引用及关系 | Evidence、Claim、Relation | P0 |
| 研究工作流 | 编排 Agent，形成分析和反方审查结果 | Workflow、AgentRun、Analysis | P0 |
| 报告与预警 | 生成研究卡片、简报并按规则分发 | Report、Alert | P0 |
| 持续跟踪 | 匹配新信息、唤醒事件、记录结论变化 | Trigger、Revision | P1 |
| 评估与治理 | 评估质量、成本、模型与提示词版本 | Evaluation、Dataset、Policy | P0 基础版 |
| 平台基础能力 | 身份、权限、配置、审计、任务和可观测性 | User、Role、AuditLog | P0 |

P0 表示 MVP 必需；P1 表示链路稳定后进入下一阶段。

## 3. 数据接入域

### 3.1 来源管理

维护数据源类型、可信等级、抓取频率、许可约束、健康状态和降级策略。来源配置不得散落在采集代码中。

### 3.2 采集任务

支持 RSS、交易所公告和授权新闻接口。每次采集保存批次号、抓取时间、源发布时间、原始地址和内容校验值。

### 3.3 文档标准化

统一编码、时区、标题、正文、附件和元数据；保留不可变原文。PDF、HTML 等解析结果必须与原文件建立版本关系。

### 3.4 内容去重

分为三层：精确 Hash 去重、近似文本去重、同一事件跨来源聚类。去重只合并展示，不删除原始文档或来源关系。

输入：外部文档或数据记录。

输出：标准化 `Document` 以及 `document.ingested` 领域事件。

## 4. 事件中心

### 4.1 事件发现

从文档识别候选事件；规则负责明显类型和格式校验，Router Agent 负责存在语义歧义的分类和重要度判断。

### 4.2 事件聚类

根据实体、事件类型、发生时间和语义相似度判断文档属于已有事件还是新事件。低置信度合并必须进入人工审核队列。

### 4.3 实体对齐

将公司名称、简称、证券代码、人物和行业映射到稳定实体 ID。证券代码应包含市场后缀，禁止仅用自然语言名称作为主键。

### 4.4 生命周期管理

拥有事件状态、重要度、紧急度、负责人、版本和关联文档。其他模块不得直接修改事件状态，只能提交状态变更请求。

输入：标准化文档。

输出：`Event`、实体关系及 `event.created`、`event.updated` 消息。

## 5. 证据与知识中心

### 5.1 原始证据

保存来源、定位信息、原文片段、内容 Hash 和采集时间。引用必须能够定位到公告页码、段落或网页快照。

### 5.2 事实声明

事实不是自由文本集合，而是带主体、谓词、客体、有效期和验证状态的 `Claim`。同一事实可关联多个独立证据。

### 5.3 冲突管理

识别数字、时间、主体和口径冲突。冲突未解决时不得生成高置信度强结论；关键冲突触发人工审核。

### 5.4 知识关系

维护公司—行业、供应商—客户、产品—业务等结构化关系，并保存来源、有效期和置信度，供行业传导分析调用。

输入：文档、事实核验结果和结构化数据。

输出：可引用证据、验证事实、冲突及知识关系。

## 6. 研究工作流

### 6.1 工作流调度

根据事件类型、重要度和预算选择 Agent，控制并行、重试、超时、暂停和恢复。工作流实现细节见[工作流设计](./03-workflow-design.md)。

### 6.2 专项分析

- 事实核验：只产出事实、冲突和未验证声明。
- 公司分析：产出财务影响、持续性和情景分析。
- 行业分析：产出上下游和竞争传导关系。
- 市场预期：产出预期差、定价程度和影响期限。
- 反方审查：产出反证、脆弱假设和结论反转条件。
- 结论合成：只基于已有结构化结果生成最终结论。

### 6.3 人工审核

人工审核是工作流节点，不是线下补救。系统必须保存审核原因、修改内容、审核人和时间。

输入：事件、证据、行情和历史数据。

输出：结构化 `Analysis`、运行记录和待审核任务。

## 7. 报告与预警

### 7.1 研究卡片

展示事件摘要、关键事实、影响方向、置信度、时间范围、正反观点、证据引用和后续观察指标。

### 7.2 每日简报

按重要度、时效性、用户范围和去重规则生成 Top 事件列表。简报中的结论引用已发布的报告版本，不重新调用 Agent。

### 7.3 预警分发

按自选股、行业、事件类型和风险等级匹配订阅。分发前必须通过来源完整性、敏感措辞和置信度规则检查。

输入：已审核或允许自动发布的报告版本。

输出：站内研究卡片、简报和预警记录。

## 8. 持续跟踪

### 8.1 触发器管理

支持新公告、监管问询、关键财务指标、相对价格变化和人工触发。触发器必须记录条件、观察窗口和去抖策略。

### 8.2 局部重分析

新证据只重跑受影响节点。例如公告修正先重跑事实核验，再根据差异决定是否重跑公司分析与合成。

### 8.3 结论版本

每次变化形成新报告版本，保留旧结论、变化原因、证据差异和置信度变化，不覆盖历史版本。

## 9. 评估与治理

### 9.1 离线评估

使用带时间截面的标注数据评估分类、抽取、引用一致性、反证召回和置信度校准，禁止引入事件发生后的信息。

### 9.2 在线评估

记录延迟、成本、失败率、人工修改率，以及事件后 1、3、5、20 个交易日的相对表现。

### 9.3 模型治理

模型、提示词、工具 Schema 和评估集均需版本化。升级必须先通过回归集和影子流量，不允许直接替换生产版本。

## 10. 模块依赖约束

- 数据接入不依赖 Agent 工作流。
- 事件中心不保存报告正文。
- 证据中心不接受无来源的事实进入“已验证”状态。
- Agent 不直接写业务表，只通过受控工具提交结构化结果。
- 报告模块不自行检索或修改研究结论。
- 评估模块只追加结果，不覆盖当时的事件和报告版本。
- 平台模块提供横切能力，但不承载金融业务规则。

## 11. MVP 功能切片

首个可交付版本按端到端能力切片，而不是先开发全部基础设施：

```text
交易所公告接入
→ 五类事件识别与实体对齐
→ 原文证据与事实核验
→ 公司影响分析
→ 反方审查
→ 研究卡片与每日简报
→ 运行审计与基础评估
```

行业传导、市场预期、自动唤醒和组合影响属于后续切片。详细范围见 [MVP 范围与验收标准](./05-mvp-acceptance.md)。
